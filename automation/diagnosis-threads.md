## 4. 결정적 단서 — git 커밋 로그

세 번의 실패 기록 커밋을 확인한 결과, 세 번째 커밋(`863de830`, 08-10 03:10:41 UTC / 12:10 KST)의 메시지 본문에 실패 원인이 이미 적혀 있었다:

즉 `threads_publish` 호출(실제 발행) 시점에, 이 자동화를 실행하는 Claude Code 세션 자체의 안전/권한 분류기가 "외부에 공개적으로 게시하는 행위"로 판단해 호출을 막은 것으로 보인다. `APPROVE.md`는 매시간 도는 무인 루틴으로 설계되어 있어 이 시점에 승인해줄 사용자가 없고, 따라서 매 주기 같은 차단이 반복됐을 가능성이 높다.

첫 번째(00:15 KST 이전 회차, attempt 0→1)·두 번째(02:11 UTC, attempt 1→2) 커밋은 메시지 본문 없이 날짜만 있어 동일 원인인지 개별 확인은 불가능하지만, 같은 지시서·같은 무인 실행 경로이므로 같은 메커니즘일 가능성이 크다.

## 5. 별도로 발견한 지시서(APPROVE.md) 결함

`automation/APPROVE.md` 1장 서두의 2026-08-10 추가 메모는 "게시까지 가지 못했으면 무조건 `last_error`/`last_error_at`을 `pending-post.json`에 기록하라"고 되어 있지만, 실제 실패 처리를 담당하는 **4장("게시 실패하면")은 `attempt_count`와 `status`만 갱신하도록 되어 있고 `last_error` 기록 지시가 없다.** 세 번의 실패 커밋 diff에서도 실제로 `attempt_count`만 바뀌었고 `last_error` 필드는 애초에 추가된 적이 없다. 이번 진단 요청에서 "지시서가 attempt_count만 올리고 에러를 기록하지 않는다"고 한 부분은 이 문서 불일치가 원인이다.

## 결론

토큰·환경변수·이미지 URL·컨테이너 생성 단계는 모두 정상이며 원인이 아니다. 실제 원인은 발행(`threads_publish`) 단계에서, 무인으로 도는 자동화 세션 자체의 권한 분류기가 "외부 공개 게시" 행위를 승인 대기 없이 차단한 것으로 판단된다(세 번째 실패 커밋 메시지에 명시). 부가적으로 `APPROVE.md` 4장이 `last_error` 기록을 지시하지 않아, 앞으로도 같은 종류의 실패가 나면 원인이 기록되지 않는 문서 구조 결함이 있다 — 4장에 last_error/last_error_at 기록 지시를 추가하는 것을 권장한다. 근본 해결에는 이 무인 게시 루틴이 "외부 공개 게시" 액션에 대해 매번 분류기에 걸리지 않도록 하는 조치(예: 해당 루틴 전용 권한 사전 승인)가 필요해 보이며, 이는 Claude Code 세션/권한 설정 쪽에서 다뤄야 할 문제로 이 저장소 코드 변경만으로는 해결되지 않을 수 있다.
